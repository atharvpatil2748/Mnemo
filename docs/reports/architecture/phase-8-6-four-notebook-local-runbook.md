# Phase 8.6 four-notebook disposable runbook

This runbook is preparation, not a claim that the owner-run ingestion or Module 8.9.4 evaluation has executed. The protected historical notebook is in `scratch/phase8_9_decommission/2026-10-10/snapshots/registry_phase8_6.db`; the retired active store is empty. The owner authorized an isolated snapshot copy. No original notebook, source file, production database or alias is written by this workflow.

## Scope and preflight

`config/evaluation/phase86_four_notebooks.v1.json` freezes the 5 Hindi, 6 Marathi and 9 English filenames, expected 24-file source-manifest digest, original notebook identity, recovery-snapshot hash, retired-store hash and disposable actor. The 346-page English Maharashtra survey PDF, missing Hindi PDF and three governance files are excluded from the new partition. The original notebook's 24 historical source associations remain intact in the copy.

From the repository root, `.\.venv\Scripts\python.exe scripts/run_phase86_four_notebooks.py dry-run` checks the `UNINDEXED` production selector, every source size and SHA-256, the reviewed language allocation, old notebook presence, indexed source hashes, recovery snapshot, retired-store receipt, local BGE-M3 revision, the nine-case historical-query identity blueprint and output boundaries. Dry-run creates no new runtime or log directory and does not alter an existing one. Actual `run` additionally checks local CUDA availability before creating output.

The final owner command, printed in the handoff response, creates one run-specific directory under `scratch/module_894_four_notebooks/` and logs under `logs/evaluation_ingestion/`. A Windows OS lock rejects concurrent writers and is released automatically on process exit. A run marker and plan digest reject unrelated existing directories. The same command resumes an owned interrupted run. A generation interrupted in `BUILDING` resumes through the existing coordinator; a generation explicitly `FAILED` gets a new deterministic retry attempt. No failed generation is treated as active. Source ingestion uses Mnemo's ACL write lease and durable source-intent protocol. An owner revocation stops subsequent file linking or embedding batches and prevents alias activation.

On retry, the runner inventories unresolved ACL source intents **before** ordinary notebook resumption or source-link permission checks. It accepts recovery only for a failed intent whose notebook and source hash match the frozen partition, whose stored notebook matches the planned identity, and whose completed creation actor/token match the deterministic run. The existing owner-authenticated recovery lease and storage reconciliation then move the intent to `recoverable`; only afterward do ordinary `active_role()` and `permits()` checks resume. Unknown intents, revoked owners, mismatched creation/source evidence, or reconciliation failures keep the run quarantined. Recovery events and `source_recovery_receipts.json` are written in the disposable run logs; the protected snapshot and already-published associations are not rewritten by this pre-resume step.

## What the run actually processes

The three new notebooks receive governed source associations to already-indexed documents whose bytes match the dataset. Before each association, the runner compares the copied document/version/chunks, parsed boundaries, historical chunk-embedding coverage, asset occurrences and required OCR/Vision/visual derivations against the protected snapshot; it also checks current structural/provenance invariants and rehashes the source bytes immediately before ingestion. `publication_states.json` records `DISCOVERED`, `VALIDATED`, `PUBLISHING`, `PUBLISHED`, or a precise failure; restart reconciles the state with the actual SQL association instead of trusting the journal alone. Existing parsed IR, canonical chunks, OCR/Vision/CLIP derivations and original assets are **reused**, not regenerated. The runner never claims fresh parser, OCR, Vision or CLIP inference. It generates and persists new real BGE-M3 Full V2 multilingual embeddings and vector projections for evidence under all four notebook memberships using the exact local revision `5617a9f61b028005a4858fdac845db406aefb181` (1024 dimensions, L2-normalized cosine). No Ollama or Codex model processes files individually.

The first owner attempt stopped at `mahades_economic_survey_ch1_marathi.pdf` after nine associations. Its parsed image blocks could not reconstruct the original parser-v2 occurrence provenance, and re-registering those blocks conflicted with immutable catalog records. Indexed-document reuse now checks the retained original, occurrence identities, assets and block-to-asset ancestry **without publishing replacement occurrences**. A genuine missing or inconsistent retained record still fails closed. The disposable run remains `QUARANTINED` until an owner retry succeeds. On retry, the runner copies the prior root-level receipts into a numbered `logs/evaluation_ingestion/<run_id>/attempts/attempt-NNN/` archive with a digest manifest before updating live receipts; it does not reset the isolated database or discard the nine successful associations. The failed source intent is reconciled under the existing ACL process/recovery leases before publication is retried. No provider generation or alias was activated in the failed attempt.

The subsequent owner attempt published all 20 new associations but stopped before BGE-M3 generation: immutable SQLite reads saw only the checkpointed main file, omitting two Marathi and all nine English memberships still committed in the WAL. The runner now closes the source-link readers, reconciles the disposable schema, performs a checked `TRUNCATE` WAL checkpoint, and compares exact notebook/source/document/current-version ancestry and evidence eligibility in WAL-aware and immutable views for all four notebooks **before** any generation attempt. A busy/incomplete checkpoint or census discrepancy quarantines the run. The later pre-audit checkpoint remains required. This repair was tested with disposable WAL fixtures; it does not claim the owner retry or generation has succeeded.

Alias publication is separate from generation. The independent audit first checks all 20 source associations, per-document completeness, generation receipts, and embedding ancestry while **no alias is active**. A passing audit is frozen as `pre_activation_audit.json` and SHA-256-bound in `run_manifest.json`. Only then does the runner attempt the disposable alias promotion. A second independent audit checks the exact active alias. The runner then binds the predeclared identity targets to the **actual** source IDs in the copied stores; `run_state.json` becomes `SUCCEEDED` only after that binding and post-promotion verification. On an ordinary promotion/post-audit/binding exception, the runner attempts the storage layer's exact-authorization first-activation deactivation; if that recovery fails, it records the error and quarantines the run. A hard crash can leave `PROMOTING` until restart rechecks the frozen audit and exact generation. The evaluation harness refuses both `PROMOTING` and `QUARANTINED`. The alias lives only in the isolated copy. There is no cross-store atomicity, and an operator must not open the isolated store outside the gated harness while its run state is not `SUCCEEDED`.

Repair verification uses snapshot reads and isolated failure-injection fixtures. It does not constitute an actual four-notebook ingestion, a real hard-kill/restart at every boundary, or a provider/alias activation test. Those operational outcomes remain unverified until an authorized owner run and independent post-run audit; a green unit/full-suite gate alone does not certify them.

Terminal messages and `events.jsonl` identify the run, notebook, current file, reused parse/chunk counts, embedding batch progress, alias, failures and final audit. `run_manifest.json`, `run_state.json`, `file_results.json`, `document_results.json`, `provider_attempt.json`, `provider_results.json`, `provider_activation.json`, `file_audit.json`, `chunk_audit_manifest.json`, `pre_activation_audit.json`, `phase86_dere3_qrels.bound.json` and `ingestion_summary.json` remain in the run-specific logs directory. A final `PASS` requires the independent SQL/ACL audit and QREL binding; a nonzero exit is a failure, not an ingestion success.

## Post-ingestion audit and evaluation gates

`\.venv\Scripts\python.exe scripts/audit_phase86_four_notebooks.py` independently reopens the isolated stores, compares the historical notebook and documents/chunks to the recovery snapshot, verifies the 20 new source/document/version associations, source hashes, parsed IR, chunk identities and representative text hashes, owner grants and stranger denial, incomplete intents, four Full V2 generation receipts, active alias identity, embedding count and protected selector. Its results distinguish errors and repeated-text warnings. It cannot certify semantic chunk quality from insertion alone; representative chunks and language-label histograms require human inspection.

`config/evaluation/phase86_dere3_identity_qrels.v1.json` is a nine-case, versioned deterministic identity blueprint. Each case retains exact query text and a keyword anchor from `scratch/execute_phase8_6_eval.py`, plus an independently checked source-file hash and exact document/version/chunk identity and text hash from the protected snapshot. The blueprint includes Hindi, Marathi, English, cross-language, selected-subset and all-four-notebook cases. Its target is an identity/lexical anchor, **not an independently adjudicated semantic relevance judgment**. Historical 30- and 70-query result ranks are filename-level and refer to a different chunk census; they are not transferred as chunk-level grades or comparable baseline metrics. The empty `config/evaluation/phase86_dere3_qrels.template.json` remains an untouched template, not the required run input.

After the successful independent audit and alias verification, the runner resolves each target's new notebook `source_id` from the persisted association, verifies exact source/document/version/chunk ancestry, and writes `phase86_dere3_qrels.bound.json`. Its digest is recorded in both the passing summary and `SUCCEEDED` state. The evaluator defaults to that bound file, refuses missing/changed/unbound targets and re-audits current persisted data before searching. Evaluation is a **separate** step after owner ingestion; it runs no-hint ranked requests through the actual shared scoped-search application service for both canonical sparse and the disposable BGE-M3 Full V2 composition. Each result is checked against persisted membership and evidence ancestry before metrics are written. It records Recall@1/5/10, Precision@10, MRR and nDCG@10 per case and denies an ungranted principal. These scores measure retrieval of declared engineering identity targets, **not human-adjudicated semantic relevance**.

The four-notebook evaluation is not run during preparation. Retrieval quality, actual multimodal outputs and final admission remain unknown until the owner has run ingestion and the separate evaluation. The versioned identity QREL blueprint needs no further owner-supplied configuration for that engineering evaluation; human semantic relevance adjudication, broader modality cases and production/external-client certification remain outside its claim.
