## 4. Deletion implementation and dependency audit

[SQLite schema](../../../mnemo-core/mnemo/storage/sqlite.py) (around lines 92–419) stores `documents.current_hash` and `document_versions.content_hash` globally; notebook `sources` reference `documents`. `sources` cascade from a notebook, but document/version rows do not. [SQLite `delete_notebook`](../../../mnemo-core/mnemo/storage/sqlite.py) (around lines 2008–2060) transactionally removes scoped FinalQA evidence, language records, multilingual embeddings, jobs, then the notebook; its comments explicitly preserve content-addressed records authorized elsewhere. [Composite deletion](../../../mnemo-core/mnemo/storage/composite.py) (lines 603–627) refreshes memberships before delegating to SQL and attempts compensation on error. Neither operation retires external registry aliases, signed certification, global documents/versions/hashes, V2 generation aliases, cache/blob files, or all derived rows. This is the exact mismatch with the requested complete reset.

[SQLite `delete_document`](../../../mnemo-core/mnemo/storage/sqlite.py) (lines 1863–1955) is a separate transaction; it explicitly removes processing jobs, OCR/visual FTS and rows, OCR/Vision/visual derivations, language observations/derivations, and title FTS before deleting the document. It does **not** first prove that no other notebook references the document, nor does it constitute an all-generation/alias decommission. Do not sequence `delete_notebook` and `delete_document` manually on shared data. FTS title rows are contentless and explicitly maintained; normal FK cascade alone is insufficient.

## 6. Proposed ordered decommission-and-reset runbook — NOT EXECUTED

Each stage requires a separately approved implementation/run plan, exact target IDs/paths and a fresh preflight. A failed prerequisite aborts the reset. No `rm -rf`, whole-shared-DB deletion, broad scratch cleanup, or credential/key deletion is proposed.

1. **Authorize and freeze scope.** Operator approves exact production/evaluation notebook IDs, store paths, reset window and expected transport outage. Refresh process, configured store, registry, runtime owner, WAL, blob and source inventories. Abort on new/unknown notebooks, changed manifest/hash, or unowned runtime. Retain a recoverable offline snapshot plus cryptographic inventory of index DB *and WAL/SHM when applicable*, registry, aliases, signed evidence, credentials metadata (not secret values), and source manifests. Snapshot handling must avoid inconsistent live WAL copies. Recovery is restore of the full consistent snapshot, not hand-edited hash records.
2. **Quiesce all consumers by authorized operator.** Identify all MCP/HTTP/UI/worker instances and their actual open stores and mutable-workspace selections; drain requests, shut down through their lifecycle, and verify process exit, closed handles and absence of new writes/leases. Do not infer safety from PID names alone. Abort if any binding or handle remains unknown. The currently observed PIDs 22400 and 22504 are leads, not a complete service inventory.
3. **Retire serving authority before deleting data.** Through a separately approved governance operation, unpublish production certified binding/activation and evaluation `phase8_5`/`phase8_6` READY aliases, and deactivate/retire Full V2 alias sets and generation pointers for target identities. Keep credentials, keys, original manifests, certificates and historical signed evidence intact or archive them per retention policy; do not rewrite signatures. Verify old identity cannot pass startup/query resolution. If no governed retirement operation exists, implement and test it in a separate task before proceeding. Recovery requires a formally approved reactivation from a consistent snapshot, never toggling an `active` flag.
4. **Capture final quiescent baseline.** Record complete per-store notebook/source/document/version/hash IDs, table and FTS counts, generation/alias/rollback graph, binary/asset refcounts, registry digest, DB/WAL fingerprints and protected files. In the shared canonical evaluation DB, explicitly retain the cross-notebook document `7fe5d45a-8343-45b3-aeea-6f84d1984be1` until both memberships and all other refs are accounted for. Abort on WAL uncertainty, foreign-key anomalies, unrelated notes/sessions or unknown owners.
5. **Execute targeted transactional cleanup, per store.** An approved, idempotent cleanup implementation must first remove target serving pointers and generation-dependent projection/FTS/vector rows, then notebook-scoped jobs/evidence and memberships; delete document/version/hash/chunk/IR/derivation rows **only** after reference queries show no remaining authorized notebook, conversation/citation, binary, generation or rollback reference. Use FK enforcement, explicit contentless FTS cleanup and per-store transactions; verify counts, FK and FTS consistency immediately after each commit. If a store has mixed ownership, preserve non-target rows and the database file. Abort/roll back its transaction on any mismatch; do not continue to a different store and report a global success.
6. **Classify historical outputs individually.** Apply the owner/pair/input/source-hash checks to the partial two-corpus runtime after quiescence and WAL-aware inventory. Classify the 16 canaries, historical 8.5 variants, validation fixtures, caches and blobs individually. Preserve any ambiguous or evidence-retained item; do not let a repeated notebook UUID imply ownership. An unresolved scratch artifact is a reported residual, not silently in scope.
7. **Post-reset proof.** Re-open stores read-only; prove no target notebook/source/document/hash/version/derived/FTS/vector/projection/alias/index-generation reference remains where removal was required, no certified startup/query binds a retired identity, and no unrelated notebooks/operational records changed. Report `COMPLETE` only if every target passes; otherwise `PARTIAL`/`BLOCKED` with recovery action. Do not create replacement notebooks or start Phase 8.9 indexing within the reset.
